# WorkBuddy 数据全量落地 E 盘

## 目标

> 不影响 WorkBuddy 以后的打开使用，但 C 盘现在和将来都不能再有它的实际数据。

## 做法：目录联接 + 登录自愈

程序把数据路径写死在 `C:\Users\legion\.workbuddy`（Electron 的 userData 也在里面），
Windows 上唯一不动程序就能改位置的做法是 **NTFS 目录联接（junction）**：
C 盘保留原路径，但它只是一个 0 字节的重解析点，实际写入全部落到 E 盘。
删除联接即回到原状，不会连带删除 E 盘内容。

两个要点：

1. **必须把整个父目录一次性做成联接**。只在子目录上挂联接不够——
   将来程序新建一个我们没挂过的子目录时，它还是会落在 C 盘。
2. **联接不改路径，所以任何配置都不用动**。调用方看到的路径仍是
   `C:\Users\legion\.workbuddy\...`，文件系统层面自动落到 E 盘。
   这就是「搬了存储但要改路径」这件事在本方案下**不存在**的原因——
   不需要改 `mcp.json`、不需要改程序设置，原路径照常可用。

## 查询当前状态

```bat
python E:\WBData\_tools\audit_links.py
```

输出每个路径是「联接（含目标）」还是「真实目录（含文件数/体积）」。
注意判断联接必须用 `st_file_attributes & 0x400`（`ReparsePoint`），
**`os.path.islink()` 认不出 Windows junction，会返回 False**，据此会得出错误结论。
`\\?\` 与 `\??\` 是同一个路径的内核写法，比较目标前要先剥掉。

## 收尾（需要你做一次）

`.workbuddy` 是最大的一块（约 218k 文件 / 1.6 GB），
因为 WorkBuddy 自身正在运行（当前会话就跑在它上面）而无法就地搬迁，
所以交给**下次登录**的守卫一次性完成。

**操作：注销或重启**。登录后启动项会自动跑一遍，无需手动双击任何东西。
之后重新打开 WorkBuddy 即可。

验证：看 `E:\WBData\_tools\guard.log`，应出现

```
check: C:\Users\legion\.workbuddy
  copied. src=NNN dst=NNN
  junction created -> E:\WBData\home\.workbuddy
```

若出现 `ABORT: N process(es) running [...]` 说明当时 WorkBuddy 还在跑，
源码分毫未动、数据已完整拷到 E，**下次登录再补一次增量**即可，不用管。

脚本只会「先复制、确认数量够了、再删源」，不会丢数据。

## 约束与安全

- `robocopy /MOVE` **一律禁用**。跨卷时它「先拷后删源」，一旦源里还有锁文件的目录触发回滚，两边都会没。
  第一次尝试就是栽在这里（丢了 `app\` 下约 12 MB 的 Chromium 会话缓存，可再生）。
- `Ensure-Junction` 的 `-BlockIfRunning` 会**在删除源之前再查一次进程**。
  这是关键的一道保险：数据已完整拷到 E，此时发现进程还在跑就直接放弃，绝不删源。
- `guard.ps1` 是幂等的，重复运行不会做任何多余的事；日志在 `E:\WBData\_tools\guard.log`。
- 想把某个路径还原成真实目录：删掉该联接，再把 E 盘内容拷回去即可。
- 想停掉自愈：删除启动文件夹里的 `WorkBuddy-E-Guard.bat`。

## 踩坑记录（改脚本前必读）

- **PowerShell 5.1 把「无 BOM 的 UTF-8」当 GBK 读**。`.ps1` 里只要有中文注释，
  就会被解成乱码并报语法错误，而且**报的行号是错的**（会指到后面无关的行）。
  本守卫曾因此整个失效（登录时静默失败，什么都没做）。
  改完 `.ps1` 后必须重新写入 BOM：
  ```bat
  python E:\WBData\_tools\fix_ps1_bom.py
  ```
  然后用下面这段验证（不要只看有没有报错，要 0 error）：
  ```powershell
  $e=$null;$t=$null
  [System.Management.Automation.Language.Parser]::ParseFile('E:\WBData\_tools\guard.ps1',[ref]$t,[ref]$e)
  $e.Count
  ```
- **不要用 Python 批量搬大目录时依赖「磁盘剩余空间」判断结果**：本沙箱的磁盘读数被虚拟化，
  写 400 MB 数据剩余空间纹丝不动，据此得出的结论全是假的。
  只报可核查的事实（联接 `reparse=True` + 目标路径）。
- 本会话的 bash 环境缺 `/usr/bin`（`ls`、`dirname` 不可用）。在命令开头补一行即可修复：
  ```bash
  export PATH="/c/Users/legion/.workbuddy/binaries/PortableGit/versions/1.2.0/usr/bin:/c/Users/legion/.workbuddy/binaries/PortableGit/versions/1.2.0/mingw64/bin:$PATH"
  ```
- **WorkBuddy 会话里的删除操作会被自己的 `safe-delete` 钩子接管**：
  Python 的 `os.remove` / `shutil.rmtree` / `os.rmdir` 一律失败
  （`SAFE_DELETE_FAIL_CLOSED`，走回收站也救不回来）。绕法：
  删目录用 `cmd /c rmdir /s /q "<path>"`，删文件用 kernel32 的 `DeleteFileW`，
  删空目录用 kernel32 的 `RemoveDirectoryW`。
- **被进程锁住的目录删不掉，而且没有免管理员的绕法**：如果该目录正好是当前会话的
  cwd，`rmdir` / `RemoveDirectoryW` 都返回失败（句柄锁，不是权限问题）；
  `MoveFileEx + MOVEFILE_DELAY_UNTIL_REBOOT` 登记「重启时删除」需要写
  `HKLM`（管理员）—— 普通权限下不可用。**正解就是交给登录守卫**。
- **本机的 HTTP 代理环境变量会把 `127.0.0.1` 也代理掉**：用 Python 探活本地服务
  （ComfyUI 的 8188 等）必须 `urllib.request.build_opener(urllib.request.ProxyHandler({}))`
  显式绕过，否则报「连不上」，看起来像服务没起。

## 运行日志归档（`.workbuddy` 里增长最快的一块）

`.workbuddy` 内部**不能**挂子联接 —— 登录守卫对 `.workbuddy` 整体做
`robocopy /E /XJ` 时会跳过该子联接，而源侧计数仍包含其内容，
于是 `dst < src` 被判成"目标不完整"，整体搬迁会**永远 ABORT**。
所以日志改用「定期搬陈旧文件」这种无损方式（复制 → 校验大小 → 删源，删不掉就回滚）：

| 源 | 归档到 | 条件 |
|---|---|---|
| `C:\Users\legion\.workbuddy\logs` | `E:\WBData\home\.workbuddy-logs` | mtime 早于 2 小时 |
| `C:\Users\legion\.workbuddy\traces` | `E:\WBData\home\.workbuddy-traces` | mtime 早于 2 小时 |

2026-09-16 首次执行：搬走 272 个文件 / 350 MB；71 个正被当前会话占用的日志保留原位。
`.workbuddy` 整体搬到 E 之后这一步就不需要了（那之后日志天然落在 E 盘）。
